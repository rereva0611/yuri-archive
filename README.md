# yuri-archive

> 我的个人互联网空间 —— 一个长期维护的个人网站，第一阶段以百合作品档案为核心。

## 项目简介

这是一个属于我自己的个人网站。它不是"百合推荐网站"，而是我长期维护的**个人互联网空间**。

第一阶段以**百合作品档案**为核心，记录：

- 我看过的百合作品
- 我的评分
- 短评和长评
- 作品标签
- 我对作品的个人分类
- 作品详情

**为什么要建这个网站：**

1. 我想有一个真正属于自己、长期维护的空间，而不是依赖某个随时可能变化的平台。
2. 我想系统地整理和记录我看过的作品。
3. 这是我在真实项目里学习 Web 开发和 AI/Agent 协作的载体。

## 项目目标

**短期目标（MVP 阶段）**

- 跑通一个最小但完整的网站：Home、作品列表、作品详情、About 四个页面。
- 用约 20 部作品作为测试数据，验证"数据 → 页面"的流程。
- 掌握 HTML、CSS、JavaScript 和 Git/GitHub 的基础。

**长期目标**

- 逐步加入：阅读记录、个人笔记、小说《忘川》、编程项目、其他个人创作。
- 把网站打磨成一个真正好用、好维护的个人空间。
- 通过这个项目，从"让 AI 写代码"成长到"能指挥 AI Agent 完成复杂任务"。

## 当前阶段

**MVP 开发阶段。**

当前目标是跑通最小闭环，验证数据组织方式，为后续扩展打好基础。不追求功能完整，先追求"能用、能懂、能维护"。

## MVP 范围

只包含四个页面：

- **Home**：网站首页，介绍这个空间是什么。
- **百合作品列表**：展示所有已记录的百合作品。
- **百合作品详情**：展示单部作品的完整信息（评分、标签、分类、短评/长评）。
- **About**：关于我、关于这个网站。

第一阶段只准备约 **20 部作品**作为测试数据。

**明确不在 MVP 内**：搜索、筛选、标签聚合、评论、登录、后台管理、数据统计等（详见"当前明确不做"）。

## 技术栈

当前只使用以下技术，不引入其他：

- **HTML**：页面结构
- **CSS**：页面样式
- **JavaScript**：数据驱动的渲染（读取 JSON，生成列表/详情）
- **Git / GitHub**：版本控制与远程托管
- **Markdown**：写文档、写内容
- **YAML / JSON**：作品数据（MVP 阶段用 JSON）
- **Astro**：静态站点生成器（**V1 阶段引入，MVP 不使用**）
- **静态部署**：GitHub Pages 或 Netlify

**当前不引入**：React、Vue、Next.js、数据库、Docker、后端服务，以及任何当前没有必要的东西。

> 说明：Astro 是好的长期方向，但 MVP 阶段先用纯 HTML/CSS/JS 打基础，等真正感到"重复"和"数据多了不好管"的痛点后再引入。

## 内容结构

百合作品数据未来的组织方式，分两个阶段演进。

**MVP 阶段（现在）：单个 JSON 数据文件**

```
data/works.json
```

一个数组，每部作品是一个对象：

```json
[
  {
    "slug": "madoka-magica",
    "title": "魔法少女小圆",
    "originalTitle": "魔法少女まどか☆マギカ",
    "year": 2011,
    "rating": 9,
    "tags": ["魔法少女", "悲剧", "百合"],
    "category": "经典必看",
    "shortReview": "一句话短评……",
    "longReview": "长评正文……",
    "cover": "images/covers/madoka-magica.jpg"
  }
]
```

字段说明（字段名和含义还在演进，MVP 先固定一套够用的）：

- `slug`：唯一标识，用于详情页 URL（英文短横线，如 `madoka-magica`）
- `title` / `originalTitle`：中文名 / 原名
- `year`：年份
- `rating`：我的评分（1–10）
- `tags`：标签（数组）
- `category`：个人分类
- `shortReview`：短评
- `longReview`：长评
- `cover`：封面图路径

**V1 阶段（引入 Astro 后）：Markdown + 前置元数据（frontmatter）**

```
content/works/
  madoka-magica.md
  yuru-camp.md
  ...
```

每部作品一个 `.md` 文件：frontmatter 存结构化字段（评分、标签、分类等），正文存长评。这样"结构化数据"和"长文本"分开，长评再长也好维护，Astro 的 content collection 能直接读取。

**为什么这样演进**：MVP 用单个 JSON 最简单、最好懂；当作品变多、长评变长、字段变复杂时，再迁到 Markdown + frontmatter。避免一开始就上复杂结构。

## 开发原则

1. **简单优先**：能用简单方案解决的，不用复杂方案。
2. **可维护性**：代码写给人看，也写给未来的自己看。
3. **不过度设计**：不为假设的未来需求提前建复杂结构。
4. **不过早增加技术复杂度**：先解决当前真实的问题，再引入新工具。
5. **AI 辅助，但人工最终审核**：AI 写的东西要能看懂、能解释，最终由我验收。
6. **所有重大架构决定需要解释原因**：为什么用 A 不用 B，必须讲清楚，而不是"因为这样更专业"。

## AI / Agent 使用方式

这个项目同时是学习以下能力的练习场：

- **AI Coding**：用 AI 辅助写代码，但自己理解每一行在做什么。
- **Vibe Coding**：先想清楚要什么、为什么，再让 AI 动手。
- **Agent**：把明确的任务交给 Agent 执行，自己负责拆解、验收和把关。
- **Debug**：遇到 Bug 先分析原因再改，不盲目试错。
- **Code Review**：AI 改完的代码自己要能 review，AI 也帮我 review 我的代码。
- **自动化**：把重复的事情（部署、格式检查、内容生成）逐步自动化。

具体协作规则见 [AGENTS.md](AGENTS.md)。

## Roadmap

```
MVP        →  V1        →  内容扩充  →  自动化  →  AI/Agent 功能
（纯静态）    （Astro）    （更多作品）  （部署/工具）  （更复杂协作）
```

1. **MVP（当前）**：HTML/CSS/JS + JSON，四个页面，约 20 部作品，跑通闭环。
2. **V1**：引入 Astro，作品数据迁到 Markdown + frontmatter，静态部署上线。
3. **内容扩充**：加入阅读记录、个人笔记、小说《忘川》、编程项目。
4. **自动化**：部署自动化、内容生成辅助、格式检查等。
5. **AI/Agent 功能**：把 AI/Agent 协作变成项目的一部分，逐步学会指挥 Agent 做复杂任务。

## 当前明确不做

以下功能当前阶段**不做**（以后需要时再评估）：

- 搜索、筛选、排序、标签聚合页
- 评论系统、用户登录、账号体系
- 后台管理界面（先直接编辑数据文件）
- 数据库、后端服务、API
- React / Vue / Next.js 等前端框架
- Docker、CI/CD 复杂流水线
- 动画、复杂交互、炫技效果
- 多语言、国际化

## 附：一个重要的坑

**不要在主目录的 Git 仓库里操作。**

我的主目录 `~` 本身是一个 Git 仓库，里面都是个人文件。本项目的代码和 Git 提交**只在 `yuri-archive/` 这个独立目录里进行**，绝不把 `yuri-archive` 之外的文件 `git add` 进主目录仓库。
